ServeDoctor

An on-call agent for LLM serving. A local Muse Glimmer model watches a live vLLM server, escalates anomalies to Muse Spark or Muse Wonder, and applies a whitelisted fix that is verified on real requests or rolled back. Evaluated on ServeIncidents, real GPU incidents with sealed answers.

What the agent did

    How it works

    Every 30 seconds the agent gets the same snapshot an operator would see, built only from data up to that moment: the SLO, current and normal config, the change log, three minutes of metrics in 10-second steps, the GPU process table and recent engine log lines.

    1 · every 30 s
    Glimmer monitors

    The open-weights 30B model runs on the same GPU and answers "healthy" or "anomaly". It costs nothing per call.

    2 · on an anomaly
    An expert diagnoses

    Muse Spark or Muse Wonder names one of 9 root causes, cites evidence from the telemetry and proposes at most two fixes.

    3 · whitelist only
    The fix is applied

    Allowed: one engine setting change (restart), a gateway rate or prompt-length limit, stopping a GPU job this run launched, advice, or escalation. Anything else is rejected.

    4 · 150 s later
    Verify or roll back

    Requests that arrived 30–90 s after the fix must meet the SLO. If not, the change is undone and a human is paged.

    Safety boundaries

    • The agent never runs shell commands; every action is validated against fixed bounds before it executes.
    • Engine changes restart only the vLLM process group the harness started; a GPU process can be stopped only if this run launched it.
    • Paid API calls reserve their worst-case cost in a ledger before they are sent and stop at fixed caps.

    The benchmark: ServeIncidents

    Each incident is six minutes of real traffic (GSM8K questions, open-loop arrivals at half of measured capacity) against vLLM serving Muse Glimmer 30B in BF16, with one or two injected faults, recorded once per second. The true cause, onset and allowed fixes are sealed in separate answer keys that no agent sees.

    v0: 24 incidents

    8 development, 16 held-out test (13 faults, 3 healthy controls). Six fault types at three severities, plus underused-GPU and healthy controls. Tuning was allowed only on development incidents.

    Hard: 15 of 16 frozen incidents

    Built because v0 saturated. Harmless config changes on every deploy, decoy GPU jobs that share names with real culprits, four two-cause incidents, faults just over the SLO line and red-herring alerts. No tuning at all. hard-16 could not start (a generator defect) and was excluded before anything was scored.

    What we learned

      Limits

      • One GPU type, one engine (vLLM) and one served model; v0 and Hard ran on different hosts (8 vs 6 req/s capacity).
      • Hard-set scores replay recorded incidents; the live evidence is the 12 v0 repair runs.
      • 13 and 12 real incidents: differences of one incident are not meaningful.
      • Wonder's six invalid answers hit the fixed 2,048-token output cap while still reasoning.
      • One Hard incident was excluded (generator defect) and one produced no SLO breach; both are reported.
